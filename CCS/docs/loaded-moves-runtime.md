# Loaded player move observations

The experimental menu now has a read-only `LoadedMoves` component. It uses the relationships measured in Probe 01: `ActivatableAbilities.Items[]` grant handles, ability CDOs, `PendingRemove`, `NonReplicatedInstances` and `ReplicatedInstances`, selector `ComboAttackList`, `RunningAttackList` and `AdditionalAttacks`, effective ability `Montage` references and optional montage `Skeleton` references. It never loads an asset, constructs a CDO, scans all UObjects, writes an engine property or grants an ability.

Opening the CCS page starts a bounded capture. Startup captures player context and the expected grant count, then captures one of at most 256 grant CDO identities and native spec handles per tick. This keeps cold [weak-serial initialization](object-identity-runtime.md) out of a bulk grant loop. Each instance step reads one grant, with at most 16 nonreplicated and 16 replicated entries; duplicate instance pointers are observed once. Instance classes must match the granted ability class and cannot be defaults/archetypes. The handle follows UE 5.6.1's `Handle != INDEX_NONE` validity rule, rather than assuming every valid handle is positive.

Selector steps skip grants without any selector relationship and schedule one selector instance per tick, with 16 entries per relationship. The work list holds at most 256 guarded candidate jobs. Duplicate grants of the same ability class are preserved rather than choosing an arbitrary first grant. Pending-removal grants do not produce instance observations. Each following candidate step reads one effective ability object, its montage/skeleton and CPU paths. Final verification is also incremental: one grant/instance list or one candidate per tick. The reader rechecks handles, pending-removal flags, CDO/instance identities, selector positions and montage/skeleton references. Empty references and missing optional montage/skeleton fields do not create fake data. Required layout mismatches discard the capture.

Candidate steps also read the selector and effective attack's `InstancingPolicy`, optional `IsHoldAttack`, and optional `AbilityTags`. The instance phase reads the grant's `DynamicAbilityTags` separately. The retained UE 5.6.1 source exposes this field through `GetDynamicSpecSourceTags()` and `AbilityTags` through `GetAssetTags()`. These are separate observations, not a single inferred attack role. Missing fields remain unknown, distinct from false flags or empty tag containers. Each container is checked against the reflected GameplayTagContainer/GameplayTag types, reads only direct `GameplayTags` (not derived parent tags), and permits at most 64 tags with 1,024 bytes per name. Tag sets are sorted and deduplicated for order-independent rechecks. Invalid types/storage or changed candidate facts/grant tags discard the capture. Grant tag changes observed during refresh also discard the previous publication.

Actual selector/attack instances take precedence over their defaults. When an ability has no captured instance, its existing CDO is retained as explicitly labeled default metadata. An ungranted referenced class is also metadata only, with an invalid spec handle. Multiple execution instances stay separate observations. None of these cases automatically grants a slot role or combat eligibility.

The published snapshot owns CPU values only and is exposed as `shared_ptr<const LoadedMovesSnapshot>`. It records actual selector, ability class/object, montage, skeleton and equipped weapon-item paths, relationship names, selector positions, spec handles, whether selector/ability sources are instances, separate selector/attack facts and grant tags, and the observation timestamp. No UObject pointer, reflected array address or property handle survives in the published data. Private engine handles use index, serial and name validation. Capture duration spans multiple frames, so publication is not an atomic engine transaction; its incremental rechecks do not establish one atomic engine transaction or event-time ownership for a later attack.

World, controller, pawn, ASC, `ActiveWeaponItemDefinition` and `ActiveShellItemDefinition` identities invalidate observations. The weapon identity is the controller's item definition, not an assumed actor or weapon name. Both controller properties are in the retained SDK; the new generation checks still need a live run. Selector and ability instance overrides are now read, with their new reader behavior still needing a live run. Transformations within an unchanged item identity need further validation. While the CCS page remains open, discovery refreshes after five seconds. The last completed snapshot remains visible during an unchanged-player refresh, labeled as refreshing; observed handle/CDO/instance changes or failed checks discard it. It is historical metadata until the new snapshot is published, never permission to override combat. Leaving it clears observations and does no further discovery work.

Captures time out after 30 seconds to cover the added bounded read and verification phases at lower menu frame rates. Layout or generation failures retry after one second. Work duration is measured after each step; a step over 2 ms discards the result and suspends discovery until the page is reopened or the player generation changes. This cannot preempt a slow read and is not a frame-time guarantee. Core status exposes state, error, candidate count, revision and maximum measured step duration. The menu shows discovered-reference counts while compatibility checks are pending.

The runtime no longer initializes MovesetManager from the extracted catalog. Staging no longer copies that fixture. Runtime slot/Tarstone indexes remain empty, and combat availability remains false. This deliberately prevents old extracted entries from silently becoming selectable when discovery fails. Saved preset paths are retained as user data, but are not treated as verified references.

Observed references are not eligible moves. The reader preserves hold/tag facts without promoting them to a role. Unique light/heavy/finisher/charged slot routing, instantiated montage choices at execution, weapon ownership, notify/track/skeleton compatibility and combat routing still require verification. Probe 02 is prepared for registry controls. The [installation monitor](content-monitor.md) now pauses reads before its first successful observation and invalidates them after inspection failures or changed game/package metadata. A changed installation requires restart; this does not certify mounted content or byte identity. Full unloaded-asset discovery, owned Tarstone data and strong installed-content cache provenance remain separate unfinished work.

Verification is limited to Windows cross-compilation and the prior live Probe 01 evidence for the underlying reads. This new component has not run in the game. Host tests do not execute UObject access. Installation and live tests require a later stopped-playing confirmation.

A fresh read-only CSSX bridge capture verified the current Scythe light selector as ASC spec handle 128: `GetGameplayAbilityFromSpecHandle` returned the same live selector and `bIsInstance=true`. Its `GetAbilitySystemComponentFromActorInfo` returned the current player ASC, and `GetAvatarActorFromActorInfo` returned the current player pawn. The current grant-handle list contained 137 handles and was unchanged at the end of the capture. `InstancingPolicy=1` matches `InstancedPerActor` in the retained UE 5.6.1 source. Its three combo references and one additional reference were read from the instance. This proves the queried selector's relationships at those query times, not every attack, an atomic grant snapshot, the native task call site or a replacement. Raw request/response IDs are retained in `CCS/work/ability-ownership/live-reference.json`.

The UE 5.6.1 source for `GetGameplayAbilityFromSpecHandle` confirms that it resolves the passed ASC/spec handle and returns a primary instance when present, otherwise the CDO with `bIsInstance=false`. CCS's reader uses reflected instance arrays so it can observe multiple execution instances too; it does not treat the helper's single primary instance as complete discovery. Primary reference: [Epic UE 5.6 Gameplay Abilities](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-gameplay-abilities-in-unreal-engine?application_version=5.6).

A later read-only capture returned defaults for 15 Scythe attacks, all declaring InstancedPerExecution. It found no finisher tags on the returned A3/B3 finisher defaults and a shared class reference between the normal light selector's third combo position and AdditionalAttacks. This is why defaults, tags and relationship positions remain facts rather than automatic slot authority. Actual execution instances may carry different state; [Probe 03](discovery-probe-03.md) now prepares event-context observations. The reader's new fact extraction and rechecks are cross-compiled but not executed in the game.
