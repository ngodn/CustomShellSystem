# Combat runtime surface for CCS (Custom Combat System)

Written 2026-09-27 from the game's UE4SS reflected class dump (`Binaries/Win64/ue4ss/CXXHeaderDump`, build `MortalShell2-5.6.1-0+++Sparta-Depot+Main+CL93241`), the UE 5.6.1 engine source, and the CSS / CSSX / Cheat Menu native sources. Nothing here was probed against the running game; every claim cites a header, a source file, or an existing mod that already does it. Extracted class bodies with offsets live in [`../work/runtime-surface/`](../work/runtime-surface/README.md) (the README there lists the grep commands).

Vocabulary and cooked defaults (Resolve, Break, poise, seals, weapons, Tarstones) are in [`../../docs/ms2-combat-system.md`](../../docs/ms2-combat-system.md); trigger events after defensive actions are in [`../../docs/ms2-loadout-combos.md`](../../docs/ms2-loadout-combos.md). This document is about what a native DLL can reach, and how.

Legend used in the tables: **proven** = CSS, CSSX or the Cheat Menu already does exactly this in shipped code; **pattern** = same mechanism as a proven case, different target; **new** = nothing in the existing mods does it yet.

## 0. The four hard rules that shape everything below

1. **A UE4SS UFunction hook only fires for calls that go through `UFunction::Func`.** UE4SS swaps the function's `Func` pointer for its dispatcher (`reference/ue4ss-sdk-d7e7826d/deps/first/Unreal/src/UFunction.cpp`, `GetFunctionHookData`: `SetFuncPtr(&Internal::UnrealScriptFunctionHook)`). `ProcessEvent` and the Blueprint VM go through `Func`; a C++ method calling another C++ method does not. So a native `UFUNCTION` is hookable only where Blueprint (or reflection) calls it. Every native function listed as a hook target below is marked with whether a Blueprint caller is known.
2. **Blueprint functions cost a global hook; native functions cost a per-function hook.** For `FUNC_Native` functions the hook is a pointer swap on that one function. For Blueprint functions UE4SS has no per-function entry, so the loader installs one `RegisterProcessLocalScriptFunctionPostCallback` that sees every Blueprint call in the game while any Blueprint rule exists (`extensions/core/src/loader/hook_service.cpp`, the `FUNC_Native` branch versus `state->scripts`; CSS has the same split in `native/src/hook_host.cpp`). CSSX's version pre-filters with a lock-free array (`maybe_hooked`) and counts calls and time (`stats`), so the cost is visible but not zero. The measured steady cost of the whole CSSX core is 0.1 to 0.2 ms per frame (`extensions/core/docs/performance.md`, 2026-09-26 findings); the script hook has only ever been measured with combat cheats on.
3. **Everything that touches a UObject runs inside the engine tick callback on the game thread.** `RegisterEngineTickPostCallback` is the one dispatch point both loaders use (`native/src/loader.cpp` `on_unreal_init`, `extensions/core/src/loader/loader.cpp` `on_unreal_init`); UE4SS key events and `on_update` run on other threads and only set atomics (`extensions/core/docs/decisions.md` D3). CSS's walk hook checks the thread id inside the hook before touching anything (`native/src/walk_override.inl` `hook_speed`).
4. **Never keep a raw `UObject*` across ticks; never cache a weak reference keyed by path.** CSSX validates every cached handle through the object array index plus serial (`extensions/core/src/core/engine.cpp` `OwnerGuard`), and the comment above `find_optional` records that a path-keyed weak cache crashed the game within a second on 2026-09-22. Reflected call frames must use `InitializeValue` / `CopyCompleteValue` / `DestroyValue` per parameter, never `memcpy` of a struct that owns memory (`engine.cpp` `Call::Call` and `Call::~Call`); `FGameplayAttribute` is such a struct (`FString AttributeName` + `TFieldPath`, `GameplayAbilities.hpp:287`).

## 5. UI: a native Player Menu page without depending on CSSX

CSSX 1.2.0 is the reference; copy the approach, not the code path. Everything is in `extensions/core/src/core/`:

| Input | `Menu::bind_inputs`: read `InputMapping.Mappings` on the UI handler for `IA_Menu_Up/Down/Left/Right_Primary`, `IA_Menu_Left/Right_Tertiary`, `IA_Menu_Confirm_Primary/Secondary_Press`, `IA_Menu_Back`, then `EnhancedInputLocalPlayerSubsystem::QueryKeysMappedToAction` for remaps; `Menu::poll_input` polls the keys per frame with `IsInputKeyDown` while the page is showing, one action per frame, repeat 400/90 ms | the page has no character preview, so the left stick can navigate |

Alternative that avoids the tab race completely: ship CCS as a CSSX extension (ABI 3, `menu.json` schema 2, `extensions/core/docs/abi.md`) and keep the native combat engine in the extension DLL. The bridge already offers `get/set/call/hooks.add` with the `bool` and `after` rule modes and validated player ownership. What it does not offer today: pre-hooks, editing parameters, object-return overrides, native `UFunction` hooks that are not post hooks, and per-frame native work (extension `tick` is coalesced to about 10 Hz, `abi.md`). CCS needs pre-hooks and parameter edits (play rate, montage swap), so a standalone mod with its own loader is the fit; the UI recipe above is copyable without linking to CSSX.

## 6. Recommended architecture for CCS

- **Loader + hot-swappable core, one C ABI, like CSSX** (`extensions/core/src/shared/core_abi.h`, `loader/loader.cpp`): the permanent `dlls/main.dll` owns the single `RegisterEngineTickPostCallback`, the hook registry (so callbacks never point into an unloaded core), the frame ring and the hotkey atomic; `core/ccs_core-<v>.dll` owns reflection, rules, UI. Core `create` is passive; `stop` returns 0 until every owned change is restored (both loaders rely on this). Keep the loader's hook service but extend the slot with `pre`/`post` and a raw `UnrealScriptFunctionCallableContext` pass-through so the core can edit `Locals` and `RESULT_DECL`; CSS's `hook_host.cpp` and CSSX's `hook_service.cpp` are 120 and 150 lines and both only do post hooks today.
- **Do not reuse the CSSX host ABI at runtime**; reuse its code by copy (engine helpers `engine.cpp` `Call`/`field`/`find_cached`/`load`/`WeakObject`, writer thread `runtime/writer.cpp`, frame stats `runtime/frame_stats.hpp`, settings). The JSON bridge is the wrong granularity for per-attack work (rule 6 of `extension-performance-standard.md`).
- **Hooks installed at boot (after the first player controller exists):** none that are global. Install the one native pre-hook on `UAbilityTask_PlayMontageAndWaitWithNotifies::PlayMontageAndWaitWithNotifies` only when a play-rate or montage rule is enabled; the `ApplyLocalCooldown`/`ApplyGlobalCooldown` post-hooks only when a cooldown rule is enabled. Blueprint-function rules (damage payload edit, event taps) go through the global script callback: install on the first rule, remove on the last, report `calls`/`ticks` in the UI exactly as CSSX does.
- **Per attack:** nothing runs per frame. A hook callback does a pointer compare against the cached player pawn/ability owner, a table lookup keyed by `WeaponTag` and ability class, and a few field writes. Property re-application happens on events (weapon/shell/seal identity change, detected once per second from cached handles) and never by scanning objects.
- **Per frame:** the tick reads the cached pawn identity (index+serial), the menu's input poll while the page is open, and the frame ring store. Target the CSSX numbers: under 0.2 ms per frame steady, no frame over 2 ms attributable to CCS (`extension-performance-standard.md` rule 8).
- **State and files:** settings and per-weapon profiles in `Mods/CCS/state/*.json` written through a background writer (never fsync on the game thread, `decisions.md` D10); a `runtime/status.json` heartbeat for tooling; a dev channel only when `dev/enabled.txt` exists.
- **Restore discipline:** every write records the original keyed by object identity; `stop` restores in reverse and refuses unload while any hook is executing (`hook_service.cpp` `remove` returns 0 while `running`).
