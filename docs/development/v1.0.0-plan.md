# CSS 1.0.0 plan

Research record and the checks behind every claim are in
[work/v1.0.0-research/notes/evidence.md](../../work/v1.0.0-research/notes/evidence.md).

**Decided 2026-09-16:** everything ships as one 1.0.0, no intermediate 0.5/0.6. The ten
ports wait and get their convention pass once, against the finished control convention
rather than the colour-only one. Shape support is built as a general capability with no
package using it at first.

Sources: 22 Virt-A-Mate packages and their Hub pages in `reference/CSS-v1.0.0-plan/`,
the Custom Nanosuit System schema in `reference/cns-docs/`, the current CSS source, and
the installed Mortal Shell II build.

## The one-line version

VaM is not a better wardrobe than CSS. It is a different shape of thing: **one uniform
parameter store, items that compose instead of replace, and shape that the skeleton
follows.** Those three ideas are what 1.0.0 should take. Almost everything else in the
reference set is either already in CSS, already impossible here, or belongs in the
Blender toolchain rather than the runtime.

## What CSS is today

A package is one outfit. It carries variants, each variant a mesh plus material
overrides plus a colour recipe plus socket corrections. Wearing it replaces the whole
character mesh. The only thing a player can adjust is colour.

```
Outfit
  Variant[]  -> mesh, materials{slot: path}, colors, attachments{socket: offset}
```

That is a good format and every part of it survives. It is also the ceiling: one item
at a time, one adjustable property type, nothing shared between packages.

## What the research actually showed

### 1. Shape moves the skeleton, or everything under it breaks

The most useful thing in the whole reference set is a field nobody advertises. A VaM
morph is vertex deltas **plus a `formulas` list** that moves the joint centres and
orientations underneath:

```json
{"targetType": "BoneCenterY",  "target": "hip",    "multiplier": "0.01144928"}
{"targetType": "OrientationX", "target": "hip",    "multiplier": "-0.001408322"}
```

17 of the 77 morphs sampled carry them. Change the hips and the hip joint moves with
them, so colliders, physics and anything parented to a bone stay inside the new body.

This is the same problem already hit twice from the other side: seals starting 6 cm
inside a wider hip, and breast springs tuned for one body reading wrong on another. The
lesson is not "add morphs". It is: **whatever declares a body's shape must also declare
where its joints sit.** That holds even without a single slider, and it is worth writing
into the convention immediately.

### 2. Items compose, they do not replace

The Bunnysuit package is five separate items: suit, collar, cuffs, ears, tail. Each is
independently wearable, each has its own materials, its own presets, its own physics.
A body stocking, a nipple overlay and a pair of gloves stack on the same body, layered
by declared draw order and surface offset.

CSS replaces the character. That is why every Seductress tier is a separately cooked
variant: 18 variants of one outfit because "harness with skirt, no top" is a different
mesh than "harness with skirt". Composition would make most of that matrix disappear.

### 3. A shared resource layer is what makes an ecosystem

`Skynet.Addon_Textures` is 395 MB of skin detail maps that 388 other packages depend on
instead of each shipping their own. Every VaM package declares its dependencies and its
licence. CSS packages are self-contained by design, which is right for installation, and
means every port ships its own copy of everything and credits nothing in machine-readable
form.

### 4. Everything a player can touch is one kind of thing

VaM has no separate "colour system". A colour is a parameter in the same store as gloss,
alpha, cloth stiffness and morph weight. A preset is a partial dump of that store with a
flag saying whether unlisted parameters reset. CNS reached the same place from the Unreal
side with `ShapeKeys`, `MaterialToggles`, `ScalarControls`, `VectorControls` and
`TextureOptions`, but with no shared vocabulary, so every mod names things differently.

CSS has the vocabulary (`group`, `role`, `hue_locked`) and only one control type to use
it on. That is backwards, and fixing it is the real content of a new convention.

## What Mortal Shell II can and cannot do

Checked against the installed build, not assumed.

**Already reachable, proven in the current source:**

- Extra skeletal mesh components attached to the player and driven by its pose.
  `attachment_follower.inl` already does `AddComponentByClass` ->
  `SetSkeletalMeshAsset` -> `SetLeaderPoseComponent` -> `FinishAddComponent`.
  Layered accessory items need no new engine access at all.
- Arbitrary material scalars, vectors and textures with layer/blend association.
  `engine.cpp` already calls `SetScalarParameterValueByInfo`,
  `SetVectorParameterValueByInfo` and `SetTextureParameterValue`.
- Live spring state. `GetPostProcessInstance` plus `AnimGraphNode_SpringBone*` exposes
  `SpringStiffness`, `SpringDamping`, `MaxDisplacement` and `ErrorResetThresh` by name.
  `check_live_springs.py` reads them today; writing uses the same reflection path.
- Per-mesh `PhysicsAsset`, `PostProcessAnimBlueprint` and `MeshClothingAssets`, so an
  authored package already owns its physics and cloth.

**Hard limits:**

- **Stock shells have no morph targets.** Checked Harros, Harros Ghost, Eredrim,
  KnightLady V04, Sester Genessa V6 and its variants: the `MorphTargets` property is
  absent from the `SkeletalMesh` export, not empty. Shape sliders can therefore only
  ever work on meshes CSS authors cook themselves, where shape keys come in from
  Blender. There is no path to a body slider on an unmodded shell. This has to be said
  plainly in the convention or authors will waste weeks on it.
- **New containers need a game restart.** Packages install with the game closed. No
  hot-install, no downloading a dependency mid-session.
- Cloth is Chaos, configured per slot at cook time. Runtime cloth editing is reachable
  in principle and is not worth the risk.

**Do not adapt, and say why:**

- Clothing Sculpt and Morph Sculpt. Real-time GPU mesh sculpting inside the game. MSII
  is a shipping cooked build with no editor; the equivalent belongs in the Blender
  toolchain, which already exists here.
- Rigify, Puppeteer, Bone Control. Posing and animation authoring for a scene editor.
  MSII is a combat game.
- Orifice Dynamics. A collision and penetration system, out of scope for a wardrobe.
- VaM's per-vertex clothing sim. MSII has Chaos cloth. Reimplementing a second solver
  on top would be worse than what is already there.
- The dual pin wart: four of the 22 packages declare both `Creator.Package.7` and
  `Creator.Package.latest` for the same dependency. Pick one pin style and enforce it.

## Proposed shape of 1.0.0

Seven pieces. The first three are the release; the rest are what makes them usable.

### A. Items and slots, instead of one outfit

A package ships **items**. An item declares a slot and what it hides.

```json
{
  "id": "collar",
  "name": "Bunny collar",
  "slot": "neck",
  "order": 20,
  "mesh": "/Game/CSS/.../SK_Collar",
  "hides": {"slots": [], "sections": []}
}
```

- Exactly one worn item may take the `body` slot. It replaces the character mesh, which
  is what CSS does today, so every existing package is a one-item package with
  `slot: "body"` and keeps working untouched.
- Every other slot takes an accessory, attached as a follower component. Slots:
  `head`, `hair`, `face`, `ears`, `neck`, `chest`, `back`, `hands`, `waist`, `legs`,
  `feet`, and `trinket1`..`trinket4` for things with no natural home.
- `hides.sections` covers CNS's `HiddenMats` and VaM's `hideMaterial`: boots hide the
  body's foot material section so it cannot poke through.
- `order` is the layering answer. Skin-tight layers also need the VaM surface offset
  idea, which here is a cook-time authoring concern, not runtime.

This is the change that justifies the version number, and the risky one: it touches how
CSS applies anything at all.

### B. One control model

Colour controls become a special case of a control. Same envelope, same `group`/`role`
vocabulary, same save path, same preset machinery.

| `kind` | drives | notes |
| --- | --- | --- |
| `color` | dye layer | exactly what exists today |
| `intensity` | scalar material param | exists today as `kind: intensity` |
| `scalar` | any named material scalar | gloss, roughness, alpha, emissive strength |
| `vector` | any named material vector | non-dye colour params |
| `choice` | texture parameter from a declared list | CNS `TextureOptions`, VaM custom textures |
| `toggle` | material section visibility | CNS `MaterialToggles` |
| `shape` | morph target weight | authored meshes only, see C |
| `spring` | named physics group | see D |

Every control keeps `id`, `name`, `group`, `role`, `default`, and range where it has
one. The role vocabulary extends to cover the new kinds rather than being replaced.
`ControlledBy`, which CNS has and CSS does not, is worth taking: one slider driving
several controls, so an author can offer "Bust" without exposing six morphs.

### C. Shape, and the joints under it

A `shape` control drives a morph target and declares what it does to the skeleton:

```json
{
  "id": "hips", "name": "Hips", "kind": "shape", "group": "body", "role": "figure",
  "morph": "Hips", "min": 0, "max": 1, "default": 0,
  "joints": {
    "thigh_l": {"offset": [0.4, 0, 0.9]},
    "hip":     {"offset": [0, 0, 0.6], "rotation": [-0.8, 0, 0]}
  }
}
```

Offsets are at full weight and scale with the slider, which is exactly VaM's multiplier
formula in a form that reads. CSS already tracks live bone poses for the seal fix, so
the consumer side is half built. Attachment clearance, spring rest positions and socket
corrections all read from the same place.

Constraint to publish loudly: **authored meshes only.** No stock shell will ever have
this.

### D. Physics the player can tune

A package declares which springs are tunable and their safe range; CSS shows them as
two honest sliders per group, `Bounce` and `Settle`, and writes the node properties
live.

```json
{"id": "bust", "name": "Bust", "kind": "spring", "group": "body", "role": "figure",
 "nodes": ["brust001", "brust002"],
 "frequency": {"min": 1.2, "max": 2.6, "default": 1.6},
 "damping_ratio": {"min": 0.4, "max": 0.95, "default": 0.65}}
```

Frequency and damping ratio, not raw stiffness and damping, because those are the
numbers that mean something: the engine integrates at a fixed 1/120 s with unit mass, so
`f = sqrt(K)/2pi` and `zeta = D/(2 sqrt K)`. The conversion belongs in CSS, not in every
author's head.

This is also the honest answer to the residual Seductress vibration. Rather than me
guessing at a damping number between builds, the player moves a slider until it stops.

**Shipped, and checked against the engine's own source rather than assumed.**
`Engine/Source/Runtime/AnimGraphRuntime/Private/BoneControllers/AnimNode_SpringBone.cpp`
integrates `a = SpringStiffness*error - SpringDamping*velocity` with no mass term at
`FixedTimeStep = 1/120`, which is where the two formulas come from. The same file caps
damping at `1/FixedTimeStep` and scales it down past that, so a declared range whose
corner crosses 100 is refused at parse time instead of quietly disagreeing in game.

Two things came out of building it that the plan had not said:

- **A control names bones, not blueprint properties.** The nodes are properties called
  `AnimGraphNode_SpringBone`, `_1`, `_2` and so on, in compile order, and a recompile can
  shuffle them. CSS matches on the bone each node drives, so a package survives its own
  animation blueprint being rebuilt.
- **The declared default has to be the blueprint's own tuning**, or the menu opens on a
  number the body is not at. `spring_defaults()` in `tools/css_colors.py` converts a node's
  stiffness and damping back into the two sliders, so an author copies rather than guesses.

### E. Dependencies and shared resources

A package may depend on another for **resources only**: textures, shaders, a shared
body. Never for behaviour. An outfit package is art and data. Code belongs in an
extension, and extensions are what CSSX adds on top of CSS: CSS is the base and runs
without it.

```json
"requires": [{"id": "eins0fx.skin-detail", "version": "1.2", "reason": "skin normal maps"}]
```

Rules taken from watching VaM's version go wrong:

- One pin style. `version` means "this or a later compatible one". No `.latest`
  alternative form, no declaring both.
- Missing dependency is a hard refusal with a named package, author and version in the
  message, not a silent half-load.
- A dependency package is a first-class CSS package that happens to ship no items.

### F. Looks as files

Templates today are local state. A **look** becomes a small exportable file: a partial
dump of worn items and control values, plus an explicit flag for whether everything
unlisted resets. That is VaM's `.vap` with `setUnlistedParamsToDefault`, and it lets
players trade looks without trading gigabytes of packages.

### G. Credit and licence in the manifest

Every VaM package declares a licence. No CSS package does, and this collection is built
almost entirely on other people's work. Add `license`, `credits` and `source_url` as
required manifest fields, surface them in the wardrobe, and have the packaging tool
refuse a package that omits them.

## The convention document

`docs/control-convention.md` becomes one chapter of `docs/package-convention.md`:

1. **Items and slots.** Which slot a thing belongs in, what it must hide, how order
   works. One body item, accessories layered.
2. **Controls.** The control envelope, the kinds, and the extended role vocabulary.
   Colour rules move here unchanged.
3. **Shape.** Declaring morphs and their joints. The authored-mesh limit.
4. **Physics.** Which springs to expose, in frequency and damping ratio, with ranges an
   author has actually walked end to end.
5. **Presets and palettes.** Today's palette rules, extended to cover non-colour
   controls: a palette sets every outfit control of every kind, body controls stay
   optional.
6. **Dependencies.** Resource-only, one pin style, hard failure.
7. **Identity.** Stable ids, licence, credits, versioning.
8. **Checks.** `validate()` stays permissive so old packages load. `lint_convention()`
   grows with each chapter and packages fail their own build on it.

## The interface is a workstream, not a detail

Today the wardrobe is four tabs (SHELL, COLOR, ANIMATION, TEMPLATES), each page rebuilt
into a single canvas with widgets bound through one hit list. That is enough for "pick
one outfit, tint it". It is not enough for 1.0.0, and the limits are already visible:

- The tab strip **already has to slide** at four labels, because they do not fit between
  the LT/RT prompts (`inventory_view.inl:182-215`). More top-level tabs is not the
  answer; pages need their own sections inside them.
- The child-count bound bit once already, and the numbers now say exactly how. Measured
  live on 0.4.1's layout with 11 outfits installed:

  | tab | page canvas | nested | rows |
  | --- | --- | --- | --- |
  | SHELL | 39 | 101 | 11 |
  | COLOR, swatch grid open | **63** | 56 | 9 |
  | ANIMATION | 35 | 10 | 1 |
  | TEMPLATES | 33 | 14 | 2 |

  COLOR peaks at 63 against the old default bound of 64. In 0.4.0 each swatch chip took
  three widgets rather than two across a grid of up to twelve, putting that page near 75.
  Past the bound the enumeration threw, CSS reported itself unavailable and the tab left
  the strip. 0.4.1 got under it two ways at once, so the margin was never visible.

  The page canvas is about 33 of fixed chrome plus the right panel, and does not grow with
  the catalog. The nested canvases are rows at six to nine widgets each, and do.
- There is no concept of wearing more than one thing, so there is no UI for it at all.

What 1.0.0 needs built:

1. **A wear page.** Slots down the left, what is in each one, what is empty. Replaces
   "pick an outfit" as the front page.
2. **A controls page that handles all seven kinds.** Swatches exist; sliders exist;
   toggles, choice strips and grouped sections do not.
3. **A physics page.** Two sliders per declared spring group, live.
4. **Looks: save, name, export, import.** Templates already do half of this.
5. **The list and detail split is the budget.** Rows are cheap and land on a nested
   canvas; right panels are expensive and land on the page. A page that expanded every
   control at once would put the whole catalog on the page canvas, which is the shape
   that failed in 0.4.0. Every new page keeps a list on the left and one thing's editor
   on the right.

## Build order

One release, but the pieces still have to land in an order that keeps the thing running.

| Step | Work | Why here |
| --- | --- | --- |
| 1 | UI foundation: bounded page building, sections within a page, a widget budget with a real measurement | Everything else adds widgets. Fix the ceiling before piling on. |
| 2 | Control model (B) in the manifest, the loader and `css_colors.py`, with colour as the first kind | The data model everything else hangs off. Existing packages keep loading unchanged. |
| 3 | Controls page: scalar, vector, choice, toggle | First visible payoff, works on packages already installed. **Done.** |
| 3b | Rename COLOR to CUSTOMIZE, top to bottom | Forced by step 3: the tab held a switch, a texture list and a roughness slider under a word that means none of them. **Done.** |
| 4 | Live physics (D), read and write `AnimGraphNode_SpringBone*` | Self-contained, and it is the honest answer to the V2 vibration. **Done.** |
| 5 | Shape (C): Blender shape keys, morph import in `CSSImportMeshCommandlet`, `SetMorphTarget`, joint offsets | Three layers deep. The import commandlet has no morph handling today. |
| 6 | Items and slots (A): manifest, wear model, follower components, hiding | The format break. Everything before it is additive, so this lands on a working system. |
| 7 | Dependencies (E), looks as files (F), licence and credits (G) | Ecosystem layer, needs the format break to be settled first. |
| 8 | `docs/package-convention.md`, then the ten ports against it | Written against features that exist, not ones being designed. |

## The word "colour" stopped covering it

Steps 2 and 3 added switches, texture choices, material scalars and springs to a tab
called COLOR, and the plan papered over that with "colour is one kind of control". That
was a sentence written to avoid a rename, not a design. 1.0 does the rename instead.

| was | is |
| --- | --- |
| tab COLOR | tab **CUSTOMIZE** |
| manifest and state key `colors` | `customize` |
| `docs/color-convention.md` | `docs/control-convention.md` |
| `native/src/colors.{hpp,cpp}`, `ColorControl`, `ColorOptions`, `color_values` | `controls.{hpp,cpp}`, `Control`, `ControlSet`, `control_values` |
| `tools/css_colors.py` | `tools/css_controls.py` |
| request actions `color`, `reset_color` | `control`, `reset_control` |
| "Reset all colors", "Browse color parts" | "Reset all", "Browse parts" |

Nothing published breaks. The runtime and the authoring tools read `colors` whenever
`customize` is absent, the old request actions still work, a 0.4 state file still loads
with everything the player chose, and `tools/css_colors.py` stays as a shim so the
collection's package builders keep running until their convention pass. Naming both in one
place is refused rather than guessed at. Verified live: the ten installed packages, all of
which say `colors`, loaded and drew their recipes on the renamed tab.

One thing fell out of it. CUSTOMIZE is four letters longer than COLOR and pushed TEMPLATES
off the tab strip. The strip was already clipping TEMPLATES to "T" in 0.4.1, so instead of
shortening a word the labels now shrink until the whole set fits, down to a floor, and only
slide as a last resort. All four are on screen for the first time.

## What this costs the existing collection

- Ten installed packages keep loading with no change. A body-slot item is what they
  already are.
- The ten ports still need their colour convention pass, which is unfinished. Doing that
  pass against the **new** control convention rather than the colour-only one would
  avoid doing it twice.
- Seductress V2's 18 variants are the strongest argument for A, and the strongest test
  of it. Most of that matrix is "same body, different pieces on it".
