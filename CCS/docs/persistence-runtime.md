# Asynchronous preset and settings I/O

CCS's experimental menu now sends file operations to `runtime::Persistence`. Reading and parsing presets, enumerating the preset directory, saving settings and replacing/deleting preset files run on its worker. The menu consumes completed CPU results on the game thread. Startup settings/catalog reads remain outside the engine tick callback.

The worker has 32 fixed job slots. A slot stays occupied while queued, running or waiting for its result to be consumed. Commands larger than 64 KiB, invalid preset filenames, mismatched write names, unexpected read payloads, unknown operations and submissions after close are rejected. The directory listing rejects more than 1,024 valid presets or 4,096 inspected entries rather than publishing an incomplete list. Disk operations never hold the submission/result mutex.

One worker processes accepted jobs in submission order. Closing rejects new requests and drains accepted jobs; destruction joins the worker before its shared state is destroyed. This uses the joining lifetime behavior described in [WG21 P0660R10](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2019/p0660r10.pdf). Destruction can wait for outstanding disk work, so it belongs to loader teardown, not an ordinary menu/combat tick. Safe core switching still needs a nonblocking drain gate.

The menu permits one pending preset action, one listing and one settings save. Settings changes made during a save coalesce into the next snapshot. Loader teardown also queues the latest settings snapshot before draining the worker. A completed preset load is applied only if its original menu generation, player controller, handler and main menu still match. Deletion requires a separate confirmation action. Initial saves cannot replace an existing preset; replacement needs a separate confirmed request. Exclusive temporary creation and atomic destination publication protect stale-list and concurrent-creator cases. Errors are retained in `menu_file_status` and logged.

The experimental [naming and confirmation flow](preset-menu-runtime.md) now uses retained native text/button widgets and typing-aware input. Native focus, mouse/button events, gamepad behavior, final styling and menu coexistence still need live validation before activation. The old button that loaded a bundled default preset as a supposed vanilla reset has been removed: current-weapon vanilla restoration requires verified live bindings, which are still pending.

Reference patterns reviewed: [CSS background writer](../../native/src/file_writer.hpp), [CSSX background writer](../../extensions/core/src/runtime/writer.hpp), [CSSX widget reuse and bounded builds](../../extensions/core/src/core/menu_page.cpp), and [CSSX mapped input polling](../../extensions/core/src/core/menu.cpp). CCS adopts background ownership and bounded work while keeping explicit results for user file actions. CSSX's widget pooling and device-aware mapped input remain the reference for the next menu/runtime work.

Verification: ten host CTest suites pass normally and under ASan/UBSan. File tests exercise save/load/delete ordering, unconfirmed/confirmed replacement, concurrent creation, temporary cleanup, rejected data preserving existing settings, missing files, queue capacity including unread results, concurrent producers, closed-worker rejection, accepted writes surviving destruction and directory limits. Windows variants compile against the pinned SDK. These are CPU-side correctness checks, not an in-game FPS benchmark. The new DLLs have not been installed.
