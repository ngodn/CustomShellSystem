# CCS architecture reference

How to scaffold Custom Combat System (CCS), a standalone UE4SS native C++ mod for Mortal
Shell II (UE 5.6.1), on the patterns that CSS (`native/`, 1.0.0-beta.5) and CSSX
(`extensions/core/`, 1.2.0) have already proven live. Every claim below cites the file it
comes from, relative to `/home/eins0fx/development/mods/msII/CustomShellSystem/`, at the
commit recorded in `CCS/work/architecture/SOURCE-COMMIT.txt`; check that commit out if the
line numbers drift. Short file names inside a section refer to the section's directory
(`menu.cpp` in section 4 is `extensions/core/src/core/menu.cpp`). `memory:<name>.md` is the
user's note at `/home/eins0fx/.claude/projects/-home-eins0fx-development-mods-msII/memory/<name>.md`.
Nothing from CSS, CSSX or the memory notes is copied into `CCS/`.

Hard constraints CCS inherits: standalone install root `ue4ss/Mods/CCS/`, no runtime link to
CSS or CSSX, all engine access on the game thread, no disk I/O on the game thread, every
per-frame cost measured, and every trap in section 8 designed out from day one.

### 1.2 CMake structure (copy the CSSX shape)

`extensions/core/CMakeLists.txt` is the template; `native/CMakeLists.txt` is the older shape.

1. Read `VERSION`, derive the numeric `X.Y.Z` for `project()`, `configure_file` a
   `version.hpp.in` into `generated/` (`extensions/core/CMakeLists.txt:11-13,27`;
   `src/shared/version.hpp.in` defines `CSSX_VERSION`, `CSSX_VERSION_WIDE`,
   `CSSX_UE4SS_REVISION`, `CSSX_UE4SS_DLL_SHA256`).
2. Portable static library for everything that has no engine or Windows dependency
   (`cssx_runtime`: common, manifest, storage, settings, extensions, writer) with
   `POSITION_INDEPENDENT_CODE ON` so it links into the Linux test `.so` too (lines 31-43).
3. `if(NOT WIN32)` block: `enable_testing()`, one executable per C++ test file, Python
   `unittest discover`, then `return()` before any UE4SS target (lines 76-97). This is what
   makes `cmake -S extensions/core -B build/host && cmake --build build/host && ctest` work
   on Linux without the SDK.
4. `cssx_sdk` INTERFACE target: the include list and compile definitions below, plus the
   import library (lines 100-122). The definitions are load-bearing, copy them verbatim:
   `NOMINMAX WIN32_LEAN_AND_MEAN RC_UNREAL_DISABLE_CLASS_DEPRECATION_WARNINGS FMT_HEADER_ONLY
   UNICODE _UNICODE UE_GAME UE_BUILD_SHIPPING=1 UBT_COMPILED_PLATFORM=Win64
   OVERRIDE_PLATFORM_HEADER_NAME=Windows PLATFORM_WINDOWS=1 PLATFORM_MICROSOFT=1
   PLATFORM_64BITS=1 WINVER=0x0A00 _WIN32_WINNT=0x0A00`. Never define `RC_UE4SS_EXPORTS` or
   `RC_UNREAL_BUILD_STATIC` in a consumer (`docs/ue4ss-sdk.md:75`).
   Include dirs (relative to the SDK): `UE4SS/include`, `UE4SS/generated_include`,
   `deps/first/*/include` (glob), `deps/first/Unreal/generated_include`,
   `deps/first/Unreal/include/Unreal`, `deps/first/Unreal/include/Unreal/Core`,
   `sdk/third-party/{fmt/include,imgui,imguitextedit,zydis/include,zycore/include,polyhook,asmjit/src,asmtk/src,glaze/include}`.
   ImGui headers are needed because `CppUserModBase.hpp` includes GUI types; the ImGui
   `.cpp` files are compiled only when a mod draws in the UE4SS GUI (CSS does,
   `native/CMakeLists.txt:87-92`; CSSX does not). CCS should not compile ImGui.
5. `add_library(main SHARED loader.cpp hook_service.cpp)` and
   `add_library(<x>_core SHARED ...)`, both `PREFIX ""`, core links `psapi` when it
   enumerates modules (lines 124-135).

Vendor/SDK paths are cache variables (`CSSX_VENDOR`, `CSSX_SDK`, `CSSX_UE4SS_IMPORT_LIBRARY`)
so a release build can pass absolute paths (`tools/cssx_release.py:167-170`). CCS should
default them to `CCS/vendor` and `CCS/reference/...` symlinks or copies, not to `../native`.

Host and cross builds (`extensions/core/CMakeLists.txt:5-9`, `tools/cssx.py:77-86`):

```sh
cmake -S CCS -B CCS/build/host && cmake --build CCS/build/host && ctest --test-dir CCS/build/host --output-on-failure
cmake -S CCS -B CCS/build/windows -G Ninja -DCMAKE_BUILD_TYPE=Release \
      -DCMAKE_TOOLCHAIN_FILE=$PWD/CCS/toolchain-clang-cl.cmake -DCCS_DEV=OFF
cmake --build CCS/build/windows -j 8
```

`-DCCS_DEV=ON` builds into a separate `build/windows-dev` tree (`cssx.py:78`); a CMake
option is sticky in the cache, which is why CSS keeps a second build dir for dev cores
(`memory:driving-css-menu-headless.md`).

### 1.3 How the DLL reaches the game

UE4SS starts every `Mods/<name>/dlls/main.dll` that has an `enabled.txt` beside it, in no
defined order; `mods.txt` entries start first (`extensions/core/docs/decisions.md:9-12`). On
this machine `mods.txt` lists only the stock Lua mods; CSS and CSSX are enabled purely by
`enabled.txt`. `enabled.txt` is an empty file (`tools/css_release.py:70-71`).

Install layout, CSSX flavour (`decisions.md:14-32`), which CCS copies with `CCS` in place of
`CSSX`:

```text
ue4ss/Mods/CCS/
  enabled.txt            activation marker
  dlls/main.dll          permanent loader
  core/ccs_core-<v>.dll  replaceable core (dev builds: ccs_core-<v>-dev-<sha12>.dll)
  core.json              {"file": "ccs_core-<v>.dll"}
  settings.json (+.bak)  user settings
  state/                 durable state (+.bak)
  logs/ccs.jsonl         rotated JSON-lines log
  runtime/               loader.json, status.json, request/response.json (dev), frames.json (dev)
  dev/enabled.txt        optional: dev channel on
  CCS.log                loader log (plain text)
  README.txt, THIRD_PARTY_NOTICES.txt, release.json
```

The stage tool (`tools/cssx.py:88-183`) is the model for `CCS/tools/ccs.py stage`:
verify the installed `UE4SS.dll` hash against the pin before touching anything (line 90);
back up the loader to `work/backups/<stamp>/` and refuse to replace `dlls/main.dll` while the
game runs unless `--core-only` (lines 96-108); name the core with the build hash so
`LoadLibrary` never sees a reused path (line 109); keep the newest four cores for one-edit
rollback (lines 113-117); write `core.json` last (line 172) so the change notification fires
after the DLL is complete; then wait for `runtime/loader.json` to acknowledge the exact core
name (lines 177-182). Game detection reads `/proc/*/cmdline` for
`MortalShell2-Win64-Shipping.exe` (`cssx.py:52-63`), never `pgrep -f`
(`memory:pgrep-f-matches-itself.md`). Game path:
`/mnt/eins0fxE/SteamLibrary/steamapps/common/Sparta/MortalShell2` (`cssx.py:31`).

## 2. Runtime architecture

### 2.1 Loader and core split

The permanent loader (`dlls/main.dll`) owns exactly four things: the one engine tick
callback, the frame-interval ring, the hook service and core selection; everything else lives
in the replaceable core (`extensions/core/src/loader/loader.cpp:1-3`, `decisions.md:40-59`).
Reason: callbacks registered with UE4SS must never point into code that can be unloaded.

Loader lifecycle (`loader.cpp`):

- Constructor (100-126): resolve the mod root from the module's own path
  (`GetModuleHandleExW(GET_MODULE_HANDLE_EX_FLAG_FROM_ADDRESS ...)`, two `parent_path()`
  hops from `dlls/main.dll`), set `ModName/ModVersion/ModDescription/ModAuthors`, register a
  plain-key hotkey through UE4SS input (`register_keydown_event`, only F1-F9/F11/Ins/Del/
  Home/End/PgUp/PgDn are accepted, lines 54-65), and open a non-recursive
  `FindFirstChangeNotificationW` on the mod root so `core.json` edits wake it without
  polling (lines 120-124). "Engine untouched until Unreal initialization" (line 125).
- `on_unreal_init` (127-145): `RC::Unreal::Hook::RegisterEngineTickPostCallback(lambda,
  {false,false,STR("CSSX"),STR("CoreDispatch")})`. The lambda: one `QueryPerformanceCounter`
  and one ring store, take the shared `recursive_mutex` gate, check the shared `alive` token,
  record the game thread id in the hook service, switch cores if the selector is dirty, then
  `api_->tick(core_, engine, delta)` inside `try/catch`.
- `on_update` (150-164): runs on UE4SS's update thread. Zero-timeout
  `WaitForSingleObject(watch_,0)` sets `selector_dirty_`; in dev mode dumps
  `runtime/frames.json` every 10 s so a loader-only configuration can be measured
  (`decisions.md:144-152`).
- Destructor (165-177): mark dead and quiesce hooks under the gate, unlock, `UnregisterCallback`
  (it may wait on a callback that wants the gate), relock, close the watch, `destroy` the
  core. "Shutdown is not guaranteed to be on the game thread: never call engine functions
  here" (line 173). CSS's loader says the same (`native/src/loader.cpp:159-161`).
- Exports (179-180): `extern "C" __declspec(dllexport) RC::CppUserModBase* start_mod()` and
  `void uninstall_mod(RC::CppUserModBase*)`.

`switch_core` (75-98), always on the game thread: `LoadLibraryExW(path, nullptr,
LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR | LOAD_LIBRARY_SEARCH_DEFAULT_DIRS)`, `GetProcAddress("cssx_core_api")`,
reject unless `abi == CSSX_CORE_ABI`, `size >= sizeof(CssxCoreApi)` and all four function
pointers are set, `create(&host_)` passively, then `stop()` the old core; a refused stop
cancels the switch and retries next tick (`stop_pending_`); on success `destroy`,
`FreeLibrary`, and write `runtime/loader.json` with `durable=false`. Failure logs never
repeat the same message (`observed_`, line 139). CSS's `reload()` is the same algorithm
(`native/src/loader.cpp:58-86`), fed by a 250 ms `core.json` poll instead of a change
notification (126-148); CSSX's notification design is the one to copy.

The loader/core contract is plain C (`extensions/core/src/shared/core_abi.h`):
`CssxLoaderHost {abi,size,root,mods_root,loader_version,log,hooks,frames,hotkey_context,take_hotkey}`
(43-57) and `CssxCoreApi {abi,size,version,create,tick,stop,destroy}` (59-70). `stop` returns
1 only when every owned change is restored; 0 keeps the DLL loaded and the loader retries.
Every call is serialised by the loader on the game thread except `create`, which "may run
off the game thread" (line 63): construct passively, touch no engine object in the constructor.

### 2.2 Core tick and lifecycle hooks

`cssx::Core::tick` (`extensions/core/src/core/core.cpp:118-168`) is the per-frame spine:

1. `Phase whole(phase_tick_)` RAII timer (line 119, struct at 12).
2. `idle_` short-circuit for A/B measurement (125).
3. One-time `started_` block: warn if `Version::IsAtLeast(5,6)` fails, detect coexisting
   mods, construct the menu, start subsystems (126-139).
4. `player_=player_context(engine)` every tick (140): `GameViewport -> World ->
   GameplayStatics.GetPlayerController(0) -> Pawn`, the controller validated through a
   `WeakObject` round trip (`engine.cpp:281-294`). This is the whole world/pawn change
   detection: consumers compare pointers frame to frame. CSS's `Appearance::player`
   additionally bumps `player_revision` when pawn, mesh component or controller change and
   caches the shell tag string by raw `FName` bits (`native/src/engine.cpp:497-534`).
5. Dev channel poll (141).
6. Hotkeys sampled at 30 Hz only while a player controller exists (156-165): a chord fires
   when every key is down and at least one was up on the previous sample (103-117), plus the
   loader's raw UE4SS key count (162-163).
7. Menu tick (166), status publish every 5 s through the writer (167).

No LoadMap/BeginPlay hooks are used anywhere in CSS or CSSX; the SDK offers them
(`reference/ue4ss-sdk-d7e7826d/deps/first/Unreal/include/Unreal/Hooks/Hooks.hpp:235-236,247-248`)
but the proven pattern is cheap per-tick reads with weak validation: the menu forgets its
attachment when `player.pc != pc_` or its `main_` widget died (`menu.cpp:320`), the HUD
service re-verifies its widget at 4 Hz or when the controller changes (`hud.cpp:52-60`),
CSS re-attaches its Inventory page after checking the controller and menu objects every 500 ms
(`native/src/inventory_view.inl:1665-1671`). A pawn identity change is the "travel"
signal; a `CharacterId` tag change is the "shell changed on the same pawn" signal (sever to
Harbinger reuses the pawn, `memory:harbinger-and-dungeon-apply-guard.md`).

Every subsystem call inside the tick follows the `sync_*_safely` shape from CSS
(`native/src/core.cpp:120-223`): rate limit with a deadline, `try` the work, on failure log
the message only if it differs from the last one and push the deadline out by 1 s. The
outer tick logs each distinct exception once (`core.cpp:314-321`, CSSX) and CSS resets its
pending state and republishes status on a tick failure (`native/src/core.cpp:1018-1028`).

### 2.3 Frame budget model and measurement

Instrumentation is always on and costs one QPC read and one store per frame
(`decisions.md:77-88`):

- Loader ring: 8192 intervals between consecutive tick callbacks (`loader.cpp:30,39-41,130-132`),
  exposed to the core as `CssxFrameRing` (`core_abi.h:35-41`).
- Core phase rings: `FrameRing<4096>` per phase (`core.hpp:52`), `Phase` RAII (`core.cpp:12`).
- `summarize()` gives count, mean, median, p95, p99, max, min, hz, hitches (> 2x median)
  (`runtime/frame_stats.hpp:25-39`).
- `frame.stats` (`core.cpp:169-215`): engine summary for the last N seconds, per-phase
  mean/max/p99 in microseconds, hitch attribution (for each frame above twice the median,
  the core's own microseconds in it; `frames_where_core_exceeds_quarter`), the same window
  sorted by core time, hook-service call counts, per-op request accounting (top 40 by
  microseconds), and menu build counters. `hitches.py` prints it
  (`extensions/core/tools/hitches.py:33-43`); `fps_probe.py` does capture/noise/compare with a
  noise floor from repeats (`fps_probe.py:68-97`).

Budgets that shipped (`docs/extension-performance-standard.md:68-71`, `docs/ui-standard.md:112-124`,
`docs/performance.md:17-24,149-166`): closed menu about 3 us per frame (one cached
`bOpen` read); menu open 50-60 us (key poll); a periodic job well under 0.1 ms per tick at
10 Hz; any single tick over about 2 ms is a hitch to move or justify; p99 within 1.5x
baseline and zero framework-attributed hitches is the acceptance gate
(`performance.md:91-96`). Median-only comparisons are not accepted; p99 and the worst frame
are what the player feels.

The eight rules in `extension-performance-standard.md:28-71` apply to CCS unchanged: cache
every reflected handle; cache invariants (CDOs, class layouts, asset paths) for the process;
fewer coarse `ProcessEvent` calls, read a count before decoding a list; no heap allocation on
the per-frame path; event-driven not polling; hot work native and cached; never touch the
disk on the game thread; budget and measure every feature.

### 2.4 Writer thread and disk policy

`cssx::Writer` (`extensions/core/src/runtime/writer.{hpp,cpp}`): one worker thread, jobs are
`replace(path, bytes)` (temp file + `MoveFileExW(MOVEFILE_REPLACE_EXISTING)`, no fsync, a
newer replace of the same path supersedes a queued one, `writer.cpp:16-23,48-57`) and
`append(path, line, max_bytes, backups)` (rotation `.1`..`.N`, `58-69`). Without `start()`
every call runs synchronously (tests). The `Core` declares `writer_` before `storage_` so it
outlives every user and is joined in `~Writer` (`core.hpp:31-32`, `writer.cpp:11-15`).
`Core::publish_status` goes through `writer_.replace` (`core.cpp:224`); every log line goes
through `Storage::log -> writer_->append` (`storage.cpp:43-53`).

Why (`decisions.md:161-169`, `performance.md:1-15,174-185`): the 5 s status write used
`FlushFileBuffers` plus a write-through rename on the game thread, an fsync under Proton,
and showed as periodic drops a median could not reveal. Only explicit user actions
(settings save, state save) keep the durable path (`common.cpp:25-53`, `durable=true`).

CSS chose the other placement: the loader owns a `css::FileWriter` thread and hands the
core `CssHost::write_file` (host ABI 2) because the CSS core contract forbids core threads
(`native/src/file_writer.hpp`, `native/src/api.hpp:8-19`, `docs/native-development.md:34-48`).
CSSX's core-owned writer survived eight live core switches in one session
(`docs/integration-tests.md:17`), so CCS takes the CSSX design: the core owns the writer and
joins it in its destructor, which the loader calls from `destroy` after `stop` succeeded.
Dev switch `dev/no-writer.txt` disables it for A/B (`core.cpp:20-24`).

### 2.5 Persistence, logging, status, recovery

Atomic JSON (`runtime/common.cpp:25-53`): `create_directories`, write `<path>.tmp`, optional
read-back compare, optional `.bak` copy of the previous file, `FlushFileBuffers` and
`MOVEFILE_WRITE_THROUGH` only when `durable`, else a plain `MoveFileExW`. Read side caps
files at 1 MiB (`common.cpp:19-24`). Settings (`runtime/settings.cpp:54-67`): missing file
writes defaults, invalid file falls back to `.bak`, else defaults, and unknown keys
round-trip through `extra` so a newer file survives an older core (`settings.hpp:6-18`).
CSS's `load_state` also archives a damaged primary as `.corrupt-<stamp>` (keeps three) and
never overwrites a good backup with it (`native/src/data.cpp:132-158`).

Logging: loader log is a plain text file with a mutex (`loader.cpp:21-29`); CSS keeps its
loader log open for the session and rotates it at 2 MB on start
(`native/src/loader.cpp:18-34`). Core log is JSON lines
`{"time","level","extension","message","fields"}` rotated at 1 MiB with five backups
(`storage.hpp:5`, `storage.cpp:43-53`); errors and warnings are mirrored to the loader log
(`core.cpp:33-36`). OutputDebugString is invisible under Proton (`core.cpp:315-316`).

Status files: `runtime/loader.json` `{abi, core, core_version, loader_version, pid, tick_ms}`
(`loader.cpp:96-97`); `runtime/status.json` every 5 s with version, pid, uptime, player
present, menu state, coexistence flags, diagnostics (`core.cpp:216-224`). CSS writes its
status on change plus a 2 s heartbeat and lets fast-changing timing counters through at most
every 10 s (`native/src/core.cpp:86-90,938-979`). Tools wait on these files by id or name
(`cssx.py:185-195`).

Recovery patterns worth copying: `css::Recovery` exponential backoff `500 ms << n`, capped
at 8 s, cleared on success (`native/src/recovery.hpp`); per-subsystem "log each distinct
error once, retry after 1 s" (`native/src/core.cpp:120-151`); a failed UI integration
detaches and retries after 2 s instead of disabling itself (`native/src/core.cpp:612-628`);
a core `stop` that refuses while a hook slot is executing (`bridge.cpp:516-524`,
`hook_service.cpp:112`); `PlayerRecovery` observes a lock nine times at 1 Hz before acting
once, keys attempts per (pawn, effect), and never repeats (`native/shared/player_recovery.cpp:49-95`).

### 2.6 What CCS must not repeat from the CSS host ABI

CSS's `CssCore` table has `render` for the UE4SS ImGui tab and `noexcept` on every callback
(`native/src/api.hpp:20-27`); CSSX dropped the tab. CSS's `css_get_api2` opt-in dance exists
only for loader/core version skew during hot swaps (`native/src/loader.cpp:63-66`); CCS
starts at ABI 1 with `size` in every struct and grows by appending members, as CSSX does.

## 3. Reflection and hooking toolkit

All of this is game-thread only; nothing assumes a header struct layout for game objects,
layouts and offsets come from live reflection (`extensions/core/src/core/engine.hpp:2-4`).

### 3.1 Finding objects and classes

`WeakObject` (`engine.hpp:47-53`, `engine.cpp:111-124`) is `FWeakObjectPtr` plus a serial
initialisation through a reflected `Conv_ObjectToSoftObjectReference` call, because UE4SS's
serial-allocation fallback uses a legacy layout. Consequence: constructing a `WeakObject`
issues a reflected call, so it must never be built inside a lookup cache (it re-enters the
cache and, live, "killed the game within a second", `performance.md:167-172`,
`engine.cpp:28-29`). Read-only guards (`OwnerGuard`) are the only safe cache validator.

### 3.2 Reading and writing properties

- `field(object, name, sizeof(T))` resolves `FProperty*` by `(class, name)` through a
  transparent-hash cache validated by `OwnerGuard`, then checks `GetElementSize()==size` and
  `GetArrayDim()==1` on every call (`engine.cpp:78-100`). `read<T>` memcpys from
  `object + GetOffset_Internal()` (`engine.hpp:35-39`). `object_of` and `bool_of` return
  null/fallback instead of throwing (`engine.cpp:101-110`).
- CSS keys struct objects by themselves, not by `UScriptStruct`, or every struct's "Size"
  collides (`native/src/engine.cpp:131-137`), and caches misses in `optional_field`
  (`161-170`). Take both.
- `raw_value<T>` writes trivially copyable values by memcpy (`engine.hpp:103-107`);
  `object_property` writes a `UObject*` through `CopyCompleteValue` (`engine.cpp:197-200`);
  `text_property` builds an `FText` with `KismetTextLibrary.Conv_StringToText` and
  `SameType`-checks before copying (`258-265`); `copy_property` copies one reflected member
  between two objects of the same type (`253-257`).
- `member(data, bytes, struct_object, name, value)` writes a field inside a struct buffer
  (a call parameter, a nested `FSlateBrush`) after a bounds check (`engine.hpp:97-102`); the
  struct object is `find_cached(L"/Script/InputCore.Key")` and the like.
- Blueprint fields with numeric suffixes (`SpringBone_1`, `SpringBone_2`) need
  `property_in()`, which walks `GetSuperStruct()` comparing full `FName`s, because
  `GetPropertyByNameInChain` compares only the base index (`bridge.cpp:30-40`).
- Maps: `MapView` validates `FScriptMap` layout bounds and iterates `IsValidIndex`
  (`bridge.cpp:41-53`); gameplay-tag keyed maps read the tag as the first `FName` of the pair
  (`native/src/misc_visibility.inl:170-203`).
- Arrays: `FScriptArrayHelper(array_property, data)`; CSSX writes elements only at the same
  count (`bridge.cpp:263-272`) while CSS resizes through `(*GMalloc)->Realloc` because the
  allocator's resize helper is not exported by the pinned import library
  (`native/src/engine_bridge.inl:185-205`).

Struct pitfalls, each one a live crash or bug:

1. Never round-trip a non-POD struct through a temporary copy. `set` stages only
   `CPF_IsPlainOldData` properties in a `Value` buffer; anything holding maps, arrays or
   strings is encoded in place, because the copy freed the Movement struct's map storage and
   the next read crashed (`bridge.cpp:396-414`, `performance.md:169-172`).
2. `FGameplayTag` is one `FName` (8 bytes in this build) named `TagName`; read it with
   `read<FName>` and compare raw bits (`native/src/engine.cpp:511-515`).
3. Never reinterpret a resolved `UClass*` as a `TSoftClassPtr`; copy table fields through
   the real reflected property (`engine_bridge.inl:135-137`).
4. Default-object and archetype writes are refused (`bridge.cpp:371,397`).
5. Check `GetElementSize()==sizeof(T)` before every memcpy and bound every count
   (arrays 4096, maps 4096, strings 65536, struct fields 256, depth 12; `bridge.cpp:143-196`).
6. `FString` char arrays include the terminator; `chars.Num()-1` is the length
   (`bridge.cpp:158-162`).

### 3.3 Calling UFunctions

`Call(object, L"Name", param_count)` (`engine.hpp:56-81`, `engine.cpp:129-169`): resolves
`GetFunctionByNameInChain`, caches the `UFunction*` and its parameter `FProperty*` list per
`(class, name)` (the vector lives in the cache, so a `Call` allocates nothing), refuses
frames over 2048 bytes, `InitializeValue`s every parameter in a 16-aligned local buffer and
`DestroyValue`s them in the destructor. `set<T>(name, value)` and `get<T>(name="ReturnValue")`
size-check against `GetElementSize`; `copy(name, other_call, other_name)` moves a value
between two frames with a `SameType` check (the FText/FSoftObjectPath chain in `load`);
`run()` is `object->ProcessEvent(function, bytes)`. The parameter count must equal
`GetNumParms()` or the constructor throws, which is the cheapest signature check available.
CSS's version also memsets the frame, caches parameter name strings (`FField::GetName()`
allocates) and adds positional `set_arg` (`native/src/engine.cpp:186-269`).

Discovery from a tool: `describe {target, function}` returns each parameter's size, in/out
flags, enum entries and struct fields (`bridge.cpp:445-472`, CSS adds struct fields at
`engine_bridge.inl:380-390`); `functions {target, contains}` lists names (`bridge.cpp:430-444`);
`properties {target, inherited}` lists fields (`417-429`). `call {target, function, args,
outputs}` accepts named or positional args and decodes only the selected outputs, validated
before the call so an undecodable out-param cannot turn a successful mutation into an error
(`445-490`).

### 3.4 UFunction hooks (loader-owned)

`CssxHookService` (`extensions/core/src/loader/hook_service.cpp`) is the only code that
registers per-function callbacks with UE4SS, and it lives in the permanent DLL so a core
can be replaced without leaving callbacks into freed code (`hook_service.hpp:2-4`).

- `add(function, callback, user)` (63-105): game thread only, at most 128 slots, delegates
  refused, the `UFunction` is `SetRootSet()` while hooked (reference-counted per function,
  `roots`). Native functions get `function->RegisterPostHook(lambda)`; the lambda checks
  `enabled` and the thread id, takes the gate, and invokes the slot with
  `(c.Context, c.TheStack, c.RESULT_DECL)` from `UnrealScriptFunctionCallableContext`.
  Blueprint functions share one global
  `Hook::RegisterProcessLocalScriptFunctionPostCallback` installed on the first rule and
  removed with the last (86-100); its callback first consults a lock-free 128-entry atomic
  array of hooked `UFunction*` (`maybe_hooked(frame.Node())`, 32-43) so every other
  Blueprint call in the game costs a few loads and no mutex (`performance.md:192-195`).
- `remove(id)` (106-139): returns 0 while the slot is executing (`running`); clears the
  callable pointers first, `UnregisterHook` only if `Internal::GetHookedFunctionsMap()`
  still holds the id, drops the root when the last user leaves, unregisters the global
  script callback when no Blueprint rule remains.
- `quiesce()` (146-150): shutdown, possibly off the game thread: clear callables, stop
  dispatch, leave engine roots to process exit.
- `stats()` (140-145): calls and QPC ticks spent in callbacks, and whether the global script
  hook is installed, so the cost is visible in `frame.stats`.

Pre-hooks that rewrite arguments: CSS's walk-speed hook
(`native/src/walk_override.inl:149-172`) calls `function->RegisterPreHook` on a resolved
`UFunction*`, reads the parameter offset from reflection once, and in the callback checks an
atomic on/off flag, the game thread id and the target component by address only (never
dereferenced from a hook), then writes `context.TheStack.Locals()+offset`. The hook keeps a
`shared_ptr` to its own atomics so a hook still registered at process exit reads a
switched-off flag instead of a freed object (`engine.hpp:346-354`). `UnregisterHook(id)`
removes it (`walk_override.inl:173-179`).

Rule-based post hooks (`bridge.cpp:90-102,493-515,532-603`): a rule binds a live target
instance (never a CDO), the player pawn and controller (`player_matches` checks
`pawn.Controller==pc && pc.Pawn==pawn`), an optional seal gate, and either a `bool` result
override (`FBoolProperty::SetPropertyValue(RESULT_DECL, value)`) or a follow-up call with an
`Owner` parameter taken from the frame's locals. A throwing rule disables itself
(`failed=true`) instead of taking the game down; `busy` guards re-entrancy; limits are 1024
rules and 128 hooked functions. This is the shape for CCS's combat hooks: resolve the
`UFunction` from a live ability instance, hook once per function, and match the owner inside
the callback.

Available UE4SS global hooks (`Hooks.hpp`): EngineTick pre/post (241-242), ProcessEvent
pre/post (203-204, global, expensive), ProcessLocalScriptFunction pre/post (223-224),
LoadMap pre/post (235-236), BeginPlay/EndPlay (247-254), AActorTick (260-261),
StaticConstructObject (193-195), InitGameState (229-230), ProcessConsoleExec (210-212).
Each returns a `GlobalCallbackId` for `UnregisterCallback`; options are
`{once, read_only, owner_name, hook_name}` as used at `loader.cpp:143`. "Broad ProcessEvent
callbacks impose work on all intercepted calls, so use them sparingly with immediate pointer
comparisons and no per-call name formatting" (`docs/native-css-research.md:25`).

### 4.2 Tab placement for CCS (after CSS and CSSX)

Order today: Inventory 0, Tarstones 1, Map 2, CSS 3, CSSX 4
(`memory:driving-css-menu-headless.md`; CSS inserts itself at index 3 with
`move_after_native`, `native/src/inventory_ui.inl:139-143`; CSSX places itself last,
`menu.cpp:98-102`). CSS attaches the first time it sees `bOpen` with no page count check
(`inventory_view.inl:1672-1679`), then orders and requires at least four pages
(`inventory_ui.inl:137`). CSSX waits for exactly `3 + css_present` pages for up to 2 s, then
attaches anyway, and throws "another mod owns the extra tab" when it sees more than four
pages before attaching (`menu.cpp:69-80`); it also refuses to order when the count is not
4 or 5 (`97`). CSS detects `css_present` by `Mods/CustomShellSystem/enabled.txt` plus
`dlls/main.dll` (`core.cpp:135`).

Therefore CCS must be the last to attach and tolerant of the count:

- Detect `css_present` and `cssx_present` the same way (`enabled.txt` + `dlls/main.dll`
  under `Mods/CustomShellSystem` and `Mods/CSSX`).
- Expected page count before attaching = `3 + css_present + cssx_present`. Wait for it;
  time out after 3 s (CSSX gives CSS 2 s, so CCS must outlast CSSX's wait) and then
  attach anyway, logging which mod never came.
- After CCS attaches, a late CSSX attach fails permanently (its `>4` check). Log this
  possibility once; the fix is CSSX-side (accept 5 pages when CCS is present) and belongs in
  the CSSX repo, not in a CCS workaround.
- Order and count checks in CCS accept 4..6 tabs; padding factor `0.6` for five or more.
- Index for CCS = `tabs.size()-1`; keep it in `tab_index_` for `navigate()`.
- A menu instance replaced by travel drops the tab; re-attach on the next open with the
  same wait (`menu.cpp:320-325`).

`Stack { box, deque<Cell> cells, used }`, `Cell { holder Overlay, vector<Item> kinds, shown }`,
`Item { kind, widget, hit, hit_left, hit_right, text_block, value_block, extra, extra2, text,
value, glyph, selected, badge, shown, enabled, icon_shown, arrows, icon, fill, color }`
(`menu.hpp:112-127`). A build runs immediate-mode page code; `take(stack, kind)` returns the
next cell's widget of that kind, creating the holder Overlay and the widget only the first
time that cell shows that kind, and toggles visibility for the rest (`menu_page.cpp:406-532`).
`ready(stack, kind)` tells the build whether the next take would create; creation is capped
at `budget_per_build=4` per build (about a millisecond per game widget) and the build sets
`deferred` to continue next frame (`401-405`, `695-727`). `finish(stack)` collapses unused
cells (`579-586`). Every write is diffed against the `Item` cache: `text()`, `show()`,
`state()` (`174-187`). Rebuild triggers are model revision, selection, section, picker or
dialog change, viewport or scale change, input-device change, never per frame
(`ui-standard.md:109-112`). `deque` because taken items must keep their address across a
build (`menu.hpp:126`).

Measured (`ui-standard.md:120-124`): selection move 0.1-0.6 ms, a section that creates new
kinds 1.5-5 ms once, dialog 4 ms then 2.4 ms, skeleton 30 ms once, versus 12-30 ms per move
before pooling.

### 4.7 Input model

- `bind_inputs()` (`menu.cpp:159-216`): read `handler.InputMapping.Mappings`
  (`EnhancedActionKeyMapping.Action` + `Key.KeyName`, offsets validated against the element
  size), map `IA_Menu_Up/Down`, `IA_Menu_Left/Right_Primary`, `IA_Menu_Left/Right_Tertiary`,
  `IA_Menu_Confirm_Primary_Press`, `IA_Menu_Confirm_Secondary_Press`, `IA_Menu_Back` to
  actions; add left-stick directions; then ask
  `EnhancedInputLocalPlayerSubsystem.QueryKeysMappedToAction` per action for the player's
  remaps. Enhanced Input rebuilds a tick after the context is added, so retry every 200 ms
  until keys appear and redraw glyphs (`menu.cpp:353-364`). CSS's table adds
  `IA_Menu_Confirm_Tertiary_Press` and `IA_Menu_Inspect` (`inventory_view.inl:110-115`).
- `poll_input()` (`221-240`): one `IsInputKeyDown` reflected call per key of the current
  device only, one action per frame, repeat after 400 ms then every 90 ms, keys yield to a
  focused text field except Escape and the controller.
- Mouse (`256-316`): OS button state through `GetAsyncKeyState` (swapped buttons honoured);
  hits are polled with `IsPressed` only while a button is down or one frame after; sliders
  drag with `GetCachedGeometry` + `GetMousePositionOnPlatform` + `AbsoluteToLocal` +
  `GetLocalSize` (`242-255`), commit on release; the wheel is
  `GetInputAnalogKeyState(MouseWheelAxis)` (`386-393`). Each hit may carry a `glyph` to
  flash and `parts` so a two-key prompt picks its direction by pointer position.
- Confirmation (`1154-1256`): the dialog is created once and kept; on open, every
  `WBP_InputListener_C` from `GetAllWidgetsOfClass(TopLevelOnly=false)` whose outer chain
  contains `WBP_Menu_Main` and that `IsEnabled` gets `SetEnabledState(false)` and is
  remembered in `frozen_listeners_`; they are re-enabled on close, and also whenever the
  page stops being active or the menu closes (`menu.cpp:333,350`). CSS freezes every
  listener in the world (`inventory_native.inl:617-630`); CSSX's outer-chain filter is the
  one to copy (`1226-1230`, fix "the Player Menu keeps its input after a CSSX confirmation",
  commit 98b0961).

### 4.8 Warm-up, reopen invalidation, textures

- `warm()` (`menu.cpp:400-422`) runs while the page is attached but another tab is showing
  (game paused, page invisible): build the skeleton when geometry is valid, import one
  texture per tick, then the first pooled builds four widgets at a time.
- On activation (`menu.cpp:338-345`): rebind inputs, arm every binding as "down" so the key
  that opened the menu is not re-read, mark dirty, and `invalidate_page()`
  (`menu_page.cpp:374-398`): every `Item` cache cleared, `setup()` re-run per item, details
  window re-`Show`n and re-sized, sentinels reset. Reason: the game re-runs each widget
  blueprint's Construct on every reopen, restoring designer text, badges, box sizes and
  brushes (`memory:menu-reopen-reconstructs-widgets.md`). Any per-widget layout
  fix must live in `setup()`, not only in creation.
- Textures (`menu_page.cpp:144-171`): `KismetRenderingLibrary.ImportFileAsTexture2D(pc, path)`
  once per file, `SetRootSet()` for the menu's lifetime, unrooted in `forget()`; an unrooted
  texture is collected when Construct drops the brushes and costs 5 ms per re-import
  (CSS: 40-55 ms per open before rooting, `inventory_native.inl:110-125`).

### 4.9 CSS specifics worth knowing

CSS's page adds a centre column with camera bar and character preview controls, swatches,
a light-edit mode and the transition animation (`native/src/inventory_native.inl:184-336`,
`inventory_view.inl`). CSS enters its tab only through native input: the game's I key opens
the Player Menu on Inventory (tab 0), then the drivers `navigate` to index 3 and assert
`status.inventory.active` before any screenshot (`memory:css-screenshot-video-workflow.md`).
The `inventory_attach`/`inventory_order` actions are always compiled; every other
`inventory_*` action is behind `CSS_INVENTORY_DEV` (`inventory_ui.inl:83-223`).

## 5. Dev workflow

### 5.1 Dev channel protocol

`DevChannel` (`extensions/core/src/core/devchannel.{hpp,cpp}`): enabled only when
`Mods/<X>/dev/enabled.txt` exists at core start (a non-dev core still serves it,
`memory:cssx-teleport-extension.md`); watches `runtime/` with
`FindFirstChangeNotificationW` and checks it with a zero-timeout wait once per tick; reads
`runtime/request.json` `{"op": ..., "id": "<unique>", ...}`; ignores a repeated or stale id
(the last id is read at start so an old request from a previous process is not replayed);
writes `runtime/response.json` `{"id", "ok": bool, "result" | "error"}` with `durable=false`.
A partially written request simply waits for the next change event (`devchannel.cpp:23`).
The client is `cssx.py request` (`cssx.py:198-204`): `id = time.time_ns()`, atomic write,
poll the response for the matching id with a 20 s timeout.

Ops (`core.cpp:240-297`): `status`, `frame.stats {seconds}`, `menu.open`, `menu.hotkey`,
`menu.key {key}` (up/down/left/right/previous_section/next_section/accept/secondary/close),
`menu.act {action}`, `menu.close`, `menu.diagnostics` (bindings, open, attached, skeleton,
tab_index, screen, widgets, builds, last/max build us, viewport, gamepad, textures;
`menu.cpp:605-614`), `engine {request}` (the bridge ops: player, find, load, class_default,
get, set, properties, functions, describe, call, table.rows, map.update, input.keys, valid),
`input.unblock {tag}`, `idle {value}`, `quiet {value}`, `quit` (`KismetSystemLibrary.QuitGame`),
and `screenshot` under `CSSX_DEV` (Steam `SteamAPI_ISteamScreenshots_TriggerScreenshot`
through `steam_api64.dll`, no focus change; `core.cpp:249-261`). Dev-only ops are compiled
out of release builds; the dev marker is never shipped (`cssx_release.py:144`).

CSS's older channel (`native/src/core.cpp:683-698`): `<mod>/request.json` `{"id","action",...}`
polled by mtime and size every 250 ms, results in `runtime/status.json` (`last_request`),
`runtime/inspection.json`, `runtime/inventory.json`, `runtime/css-probe.json`;
`tools/css.py`, `css_probe.py`, `css_frame_profile.py`. The CSSX shape (one request file,
one response file, change notification) is the one to copy.

### 5.2 Driving and screenshot tools

### 5.3 Hot-swapping a core while the game runs

`cssx.py stage --dev --core-only`: builds, copies `core/ccs_core-<v>-dev-<sha12>.dll`,
rewrites `core.json`, and the loader's change notification switches on the next tick,
acknowledged in `runtime/loader.json` (`cssx.py:172-182`, `loader.cpp:137-141`). Live A/B is
rewriting `core.json` between two staged cores (`memory:cssx-perf-measurement.md`).

the dev channel's last request/response names the dying call

closed game; a core that owns hooks must clean them in `stop()` or the loader keeps

which is why the docs call reload a developer path, not a player feature
(`decisions.md:49-52`).

### 5.5 Branches, commits, confirmation rules

- Work on `nextgen100`; `main` is the public branch modders build against and is only

## 6. Coding standards observed, and the ship checklist

### 6.1 Language and layout

- C++23, `/W4 /EHsc /permissive-`, zero warnings; one class per header, `#pragma once`, a
  top comment stating purpose and thread (`engine.hpp:2-4`, `writer.hpp:2-6`).
- Portable code (`src/runtime`) includes no engine or Windows header (`common.hpp:2-3`);
  engine code includes only the `Unreal/...` headers it uses; Windows-only pieces are
  `#ifdef _WIN32` with a POSIX branch so tests run on Linux (`writer.cpp:52-56`).
- Names: `snake_case` functions and locals, trailing underscore members, PascalCase types,
  namespaces `cssx`, `cssx::engine`; reflection names are wide literals `L"..."`; UE4SS
  strings use `STR("...")`.
- Large feature bodies as `.inl` included into one translation unit are CSS's style
  (`native/src/engine.cpp:333,494-496`); CSSX prefers separate `.cpp` files. CCS: separate
  files, one TU per feature.

### 6.2 Errors and the ABI boundary

- Inside a DLL: exceptions with descriptive `std::runtime_error` messages; every bounds
  violation throws before any write.
- Across any ABI (loader/core, C callbacks, hook callbacks): never let an exception cross;
  every exported function is `try { } catch(const std::exception&) { } catch(...) { }` and
  returns 0/nullptr (`core.cpp:308-324`, `abi.h:7-9`, `hud.cpp:243` `guard()`); CSS marks them
  `noexcept` (`native/src/api.hpp`, `hook_api.hpp:6`).
- Log each distinct failure once; back off with a deadline; never disable a subsystem
  permanently on one failure.

### 6.3 JSON and strings

- `using Json = nlohmann::json`; `.at()` for required, `.value()` for optional; validate
  type and range before use; cap request/response at 1 MiB, strings at 64 KiB, lists at
  4096, nesting at 12 (`bridge.cpp:143-144`, `client.hpp:41-43`).
- Never keep a pointer or reference into a `Json` temporary (`value(...)` returns a copy):
  `library_entries()` returns a reference into the stored snapshot for that reason
  (`menu_page.cpp:135-142`).
- Files and logs are UTF-8; the engine is UTF-16. `wide()`/`narrow()` use
  `MultiByteToWideChar`/`WideCharToMultiByte` with `MB_ERR_INVALID_CHARS` and throw on
  invalid input (`engine.cpp:12-27`); `path_utf8`/`utf8_path` for `std::filesystem`
  (`common.hpp:13-19`). `FName(wide.c_str())`, `FString(wide.c_str())`.
- Identifiers used in file names: letters, digits, `.`, `_`, `-`, at most 96 chars, no
  Windows reserved stems (`common.cpp:14-18`, `storage.cpp:56-65`).

### 6.4 Per-frame discipline

- No allocation on the per-frame path: `Call` frames are stack buffers with cached
  parameter lists; `FName`s for key names are cached (`menu.cpp:42-46`); `GetFullName`
  strings are built only when an object is first seen (`bridge.cpp:126-134`); rings are
  fixed arrays.
- Rate-limit with `GetTickCount64` deadlines; measure with `QueryPerformanceCounter`;
  portable code uses `steady_clock` (`common.cpp:68-70`).
- Poll only the cheap signal (a cached `bOpen`, a pointer compare) and do the expensive
  thing on an edge (`ui-standard.md:109-118`).
- Every reflected read validates `GetElementSize()` and `GetArrayDim()`; every list read has
  an upper bound; `IsA<>` before every cast.

### 6.5 Threads

- Engine work only inside the tick callback. Hook callbacks compare `GetCurrentThreadId()`
  with the recorded game thread and return otherwise (`hook_service.cpp:79,91`).
- Cross-thread state is `std::atomic`; the loader/core gate is a `shared_ptr<recursive_mutex>`
  with a `shared_ptr<bool> alive` token captured by every registered lambda
  (`loader.cpp:33-34,129`).
- The writer is the only other thread and it never touches the engine.

### 6.6 Tests

- Portable static library plus a plain `main()` with a `check(bool, what)` lambda that exits
  non-zero (`extensions/core/tests/runtime_tests.cpp:12-15`); temp roots under the system temp
  with a Unicode segment so path handling is exercised (line 16).
- Python `unittest` for tools, with the game process detection monkey-patched
  (`tests/test_tools.py:38`).
- What CSSX tests on the host: manifest/settings recovery, writer replace/append/rotate/drain,
  frame stats math, tool planning. CSS tests startup/state recovery, recovery backoff,
  frame profile, motion math.

### 6.7 Before you ship a build

1. `cmake` host build and `ctest` pass; Python unit tests pass; the Windows cross build is
   warning-free with the dev option off.
2. `frame.stats` over 60 s of play: zero framework-attributed hitches, core mean in the
   low hundreds of microseconds, p99 within 1.5x baseline (`performance.md:91-96,149-166`).
3. `menu_stress.py --cycles 10` passes with the Player Menu closed afterwards and no widget
   growth (`integration-tests.md:40`).
4. Open/close/reopen the menu: rows show real text, not designer defaults (Construct rerun).
5. Beacon travel with the menu closed and open: tab drops and re-attaches; hotkey still
   opens (`integration-tests.md:39,69`).
6. Sever into the Harbinger, shell switch, death, save reload with every feature on;
   gameplay effects restored by `stop()` and by "turn everything off".
7. Coexistence rows: CSS alone, CSSX alone, all three; tab order Inventory, Tarstones, Map,
   CSS, CSSX, CCS; each tab navigates.
8. Release ZIP built from the tag by the release tool and passed `verify`; the exact ZIP
   extracted and cold-started once (`docs/releases.md:29-50`).
9. `release.json` records the UE4SS pin; README states the required UE4SS build and hash.
10. Nothing in the ZIP from a live install, no state, logs, dev marker, PDBs.

## 8. Traps register

Each entry: the trap, where it was found, what the code does now.

1. Synchronous disk I/O on the game thread. A 5 s status write with fsync produced periodic
   drops. Writer thread for informational files, `durable=false` for runtime files
   (`decisions.md:161-169`, `performance.md:174-185`).
2. Caching reflected objects by path in a `WeakObject` map crashed the game within a
   second (WeakObject construction issues a reflected call and re-enters the cache).
   Read-only `OwnerGuard` caches only (`engine.cpp:28-39`, `performance.md:167-172`).
3. Round-tripping a non-POD struct through a temporary copy freed the struct's map storage.
   POD staged, everything else written in place (`bridge.cpp:396-414`).
4. Per-frame `FindFirstOf` / object-array scans (26 Hz with zero extensions). Resolve through
   properties once per generation, cache weak handles (`performance.md:42-54`).
5. `find()` by path on the per-frame input path; cached (`performance.md:188-190`).
6. Global Blueprint script hook taking a mutex on every Blueprint call; lock-free pre-filter
   (`hook_service.cpp:27-43`, `performance.md:192-195`).
7. Reading a 110-entry ability list every second (4.6 ms); count first, decode on change
   (`performance.md:137-142`).
8. Re-reflecting invariants on pawn change (10 shell definitions at 10-13 ms each, a 100 ms
   hitch); once per process, one token per tick (`performance.md:140`).
9. First menu build decoding two 1 MB banners; images shrunk, imports spread one per tick
   (`performance.md:159-163`, `menu.cpp:413-416`).
10. The game re-runs widget Construct on every menu reopen; `invalidate_page()` on
    activation and every layout fix in `setup()` (`menu_page.cpp:374-398`).
11. `SetRenderTranslation`'s parameter is `Translation`, not `InTranslation`
    (`hud.cpp:195`, `menu_page.cpp:689`).
12. Imported textures are collected when Construct drops the brushes; root them for the
    page's lifetime, unroot on forget (`menu_page.cpp:152-170`).
13. Widget creation or reparenting costs about a millisecond; pool per cell and kind,
    create at most four per build (`menu.hpp:120-132`).
14. Keeping a pointer into a `Json` temporary (`library_.value(...)`) read as null
    (`type_error 306`); return references into the stored snapshot
    (`memory:cssx-native-page.md`).
15. Glyph cache signatures must include `bindings_generation_` or prompts built during
    warm-up keep the mouse glyph (`menu_page.cpp:766,784`).
16. The details window's designer sample text and icon must be overwritten even with an
    empty description (sentinel `detail_body_="\x01"`, collapse `MyIcon` and friends)
    (`menu_page.cpp:218,342-344`).
17. A lone paragraph wraps narrow without `MinDesiredWidth` on the panel SizeBox
    (`menu_page.cpp:351`).
18. `WBP_NB_Option` value box is zero-width unless the width overrides are set
