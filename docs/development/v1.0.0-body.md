# CSS 1.0 body: real anatomy and a figure the player can set

Working document for the body work inside 1.0.0. The broader plan is in
[v1.0.0-plan.md](v1.0.0-plan.md); this covers the part that decides what the
player's body actually looks like.

## The problem, measured

The Beaute Genessa body has a good silhouette and bad anatomy. That is not an
opinion, it is three numbers taken off the shipped torso:

| region | relief above surrounding skin | what a body actually does |
| --- | --- | --- |
| `nipple_left` | **+11.29 mm** | a nipple stands 5-9 mm proud |
| `nipple_right` | **+11.97 mm** | " |
| `vulva` | **+16.66 mm** | does not stand proud at all |

Rendered close up, the nipple is an angular cone with hard creases where it meets
the breast, and no areola.

The cause is a chain, not a bug:

1. The BG3 source torso ships **holes at the nipples and crotch**, because those
   are separate submeshes in the original.
2. V2 closed them with **script-authored geometry**.
3. `skin_v2.py` painted the colour on as **sphere and ellipsoid masks** at fixed
   radii, which is why it reads as a sticker.
4. `fit_beaute_body_v2.py` then wrapped all of it onto the Beaute silhouette
   using a **robust median filter over a 5 cm neighbourhood**, tuned to reject
   the Genessa undersuit's straps as outliers. A nipple is a small,
   high-curvature feature, so the same filter treats it as an outlier too.

Step 4 is the one worth remembering: the tool that makes the body fit is the tool
that destroys the anatomy, and they cannot both run over the same region.

## Where the good anatomy comes from

Roughly 1,770 Virt-A-Mate morphs are already on this machine, and measured with
`tools/vam_morph.py` they are **one consistent topology**: Genesis 2 Female
(21,556 vertices) plus its genitalia geograft.

`samples/vam/morphs/extracted/MORPH-CATALOG.md` writes these off as
"incompatible, reference value is the NAMING". That is wrong and worth correcting
in place: incompatible with Eve's mesh, yes, which is what a transfer step is
for.

MonsterShinkai's set in particular is already modular, measured per region:

```
BodyBase        booty 1.10 cm avg   thighs 0.39   breast 0.07   <- leaves breasts alone
BodyThickness   booty 1.16 cm avg   thighs 0.17   breast 0.04
BreastL         booty 0.01 cm avg   thighs 0.12   breast 1.10 / 5.32 max
```

`BodyBase` is a figure pass that deliberately does not touch the breast, because
it is designed to stack with `BreastS/M/L`. It also carries **415 joint
formulas**, which is pillar C's `joints` block for free.

## The one missing piece

Every one of those morphs is a **delta with no original**. The Genesis 2 Female
base mesh is not in any `.var`, because every VaM install already has it.

VaM 1.22.0.13 is downloading now into `work/v1.0.0-body/vam/install`, driven
headlessly: the updater has no URLs in it, so it runs under Wine and the Install
button is clicked with `xdotool`. Demo mode is enough, the activation key gates
Hub content rather than the base figure.

`tools/harvest_g2f.py` then drives AssetRipper's headless web API to pull the
mesh out.

## Two checks that must pass before a single morph is applied

**Vertex count.** Exactly 21,556. A G2F exported at subdivision 1 gives 86,770
and looks perfectly fine, and every morph would then apply to the wrong vertices.

**Vertex order.** This is the one that actually bites. glTF splits a vertex at
every UV and normal seam, so the exported file never has the right count and has
to be welded first, keeping first-occurrence order. Whether that recovers the
*original* order is an assumption, so it is tested rather than trusted:
`gltf_mesh.morph_lands_where_expected` takes a region morph's indices and asks
whether the vertices they point at form one cluster on the mesh, comparing
against random samples of the same size drawn from the same mesh.

Measured separation on a synthetic body-shaped cloud:

```
real region        spread ratio 0.34 - 0.56   clustered
wrong order        spread ratio 1.00 - 1.01   scattered
```

A wrong order cannot pass that.

## Two different transfers, deliberately kept apart

| | figure | anatomy |
| --- | --- | --- |
| moves | whole regions, centimetres | hundreds of vertices, millimetres |
| bind | wide, 4% of body height | snug, 3 cm radius |
| smoothing | yes, feathered | **none inside the region** |
| method | `shape_transfer.transfer` | `conform_region_along_normal` |

The anatomy form projects each vertex along **its own normal** rather than to the
nearest donor point. Nearest-point is ambiguous exactly where detail lives: for a
vertex inside a bulge the closest surface point is on the *side* of the bulge, so
a nipple conformed that way comes out squashed sideways. Verified on a synthetic
bump of known height:

```
nearest point      apex reaches 11.23   (undershoots)
along normal       apex reaches 11.800  (donor is 11.80)
outside the region deviation 1.78e-15   (untouched)
```

## Tiers, not variants

Seductress V2.1 ships **48 cooked meshes**: 2 styles x 4 exposure x 3 bodies x 2
heads. Three of those bodies are one body at three points on a slider. Adding
breast and glute variety the same way gives 2,160 meshes.

`tools/vam_figure.py` makes them axes instead. Three independent axes, 100
combinations, measured for overshoot against the real library:

```
figure   breast      glutes   morphs  largest cm
game     slim        slim          1        1.68
game     busty       normal        2        3.69
game     omg         omg           4       12.33
base     slim        normal        3        2.02
```

Breast axis: Slim, Normal, Busty, More busty, **OMG!**

## Known gaps

- **Pubic hair is in none of the packs.** Morphs cannot provide it; it is a
  texture layer and will have to be authored.
- **The good textures are in G2F UV space.** The 4096² genital normal, labia and
  full-body detail maps all need the base mesh for correspondence, exactly like
  the morphs do. The one exception is `Bplus.Nipple`, a standalone square stamp,
  usable on any body as-is.
- **Cloth is cooked against the base shape**, so a large figure morph will make
  skirts drift. Needs a declared safe range per body.
- Whether welding recovers DAZ's original vertex order is assumed, not proven,
  until the order check runs against the real mesh.
